# コードとテストのレビュー手順

テストケースの変更時や一定規模以上のコード変更時に、Claudeに差分を検査させます。実装上の不備や設計原則からの逸脱、不適切なテスト修正をコミット前に検出することが目的です。

## 発火条件と実行タイミング

次のいずれかに該当する場合は、このスキルに従ってレビューを実施します。

* テストファイルの追加または修正
* 約50行以上の本番コード変更
* 複数ファイルにまたがる本番コード変更
* 重要境界に関わる本番コード変更

重要境界にはスキャンライン層の操作、ライブモードのアロケーション制約、乱数の決定論的再現性、パニック禁止規約、公開APIが含まれます。実行タイミングは `cargo fmt --all -- --check`、`cargo clippy --workspace --all-targets -- -D warnings`、`cargo test --workspace --all-targets` がすべて通った直後とします。コミットおよびPRの作成は、このレビューと指摘事項の修正を完了させてから行います。

## ステップ1 レビューの実行手段の選択と起動

状況に応じて、次の3つの手段のいずれかを選択してレビューを実行します。

* ローカルの `claude` コマンド
* サブエージェントの起動
* `swarm` ワーカーの起動

ローカルの `claude` コマンドを使う場合は、認証済みの `/Users/chikoski/.local/bin/claude` を利用します。サンドボックス外のバイナリとネットワーク通信を使用するため、`run_command` で `BypassSandbox: true` を指定して実行してください。`-p` と `--permission-mode plan` などを指定して非対話かつ読み取り専用で実行し、プロンプトにレビュー依頼内容を渡します。

サブエージェントを使う場合は、`invoke_subagent` ツールで `research` などの読み取り専用サブエージェントを起動し、プロンプトに検査対象と観点を渡します。

`swarm` ワーカーを使う場合は、`swarm` ツールの `add` アクションを呼び出して起動します。`name` には `code-reviewer`、`model` には `claude-opus-5-5-high`、`workspace` には `inherit` を指定します。`claude-opus-5-5-high` のクォータが枯渇している場合は、`claude-sonnet-5-5-high` を指定します。実行中にクォータ上限へ達した場合も、同じ代替モデルへ切り替えます。

## ステップ2 レビュー指示と検査観点

レビュー担当者への依頼内容には、変更の目的、関連するIssueやADRの番号、`git status` と `git diff` を用いてワークツリーの差分を確認する指示を含めます。あわせて、[CLAUDE.md](../../../CLAUDE.md)、[CONTRIBUTING.md](../../../CONTRIBUTING.md)、[DEVELOPER_GUIDE.md](../../../DEVELOPER_GUIDE.md) を参照するよう伝えます。レビュー担当者は読み取り専用で検査のみを行い、ファイルを直接編集せずに指摘事項を出力または `@coordinator` 宛てにボードへ投稿させます。

レビュー担当者には次の4つの観点で差分を検査させます。

* パニック禁止規約と安全性の遵守
* 設計原則と再現性の維持
* ライブモードとリソースの制約
* テストの妥当性と網羅性

パニック禁止規約と安全性では、ライブラリクレートで `unwrap`、`expect`、境界検査なしのスライス添字アクセス、ゼロ除算が持ち込まれていないかを確認させます。不正な画像バイト列や範囲外パラメータに対してパニックではなく型付きエラーやクランプまたは無操作で応答するかを点検させます。

設計原則と再現性では、エフェクトがスキャンライン層以外の圧縮ストリーム等を変更していないか、またフィルタ値再計算の有無が世代境界として明確かを検査させます。さらに、乱数を使う処理が外部から渡された `Rng` のみを参照して決定論的になっているかを確認させます。

ライブモードとリソースの制約では、定常状態のフレーム処理で不要なヒープアロケーションが発生していないかを確認させます。公開APIや `wasm` ターゲット互換性への影響もあわせて点検させます。

テストの妥当性と網羅性では、[CLAUDE.md](../../../CLAUDE.md) のルールに基づきテストのスキップや無効化、しきい値の緩和が行われていないかを入念に確認させます。`insta` のスナップショットやBLAKE3ハッシュを用いるゴールデンテストが根拠なく書き換えられていないかも確認させます。あわせて、各カラータイプ、各ビット深度、`magnitude = 0.0`、幅や高さがゼロの空入力などの境界ケースが網羅されているかを評価させます。

## ステップ3 修正とエスカレーション

選択した実行手段の出力、サブエージェントからの返答、または `swarm_wait` と `read_board` でレビュー報告を受け取ります。指摘された実装上のバグやエッジケースのテスト不足は、メインエージェントが自律的に修正します。修正後はローカルのフォーマット確認、Clippy、テストを再度実行し、すべて通ったことを確認した上で必要に応じて再確認を依頼します。`swarm` ワーカーの場合は `post_message` で `@code-reviewer` に依頼します。サブエージェントの場合は `send_message` で、ローカルコマンドの場合は修正後の差分を添えた再実行で依頼します。再確認のやり取りは最大2往復までとします。

既存テストケースやゴールデンテストの期待値を変更する必要があり、かつその変更が仕様変更やシード出力の互換性変更を伴う場合は、自律的に修正を確定してはなりません。また、設計上のトレードオフ判断が必要な指摘を受けた場合も同様です。該当する論点と変更影響を整理し、ユーザーへエスカレーションして判断を仰ぎます。

## ステップ4 後処理

すべての指摘への対応とローカルチェックの再確認が完了したら後処理を行います。`swarm` ワーカーを起動した場合は、`swarm` ツールの `kill` アクションで `code-reviewer` を終了します。その後、変更のコミットとPR作成へ進みます。
